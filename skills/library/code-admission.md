# Code admission

- Search existing code with GitNexus (`orch code search` / `orch code impact` / `orch code processes`) before creating anything. Process listing, impact, `context`, and `detect_changes` all read GitNexus 1.6 `processes` / `affected_processes` even when `process_symbols` or `processes` is an empty array. Watcher wraps and the `orch code` / plan-draft factory also recover 1.6 object rows that only have `process` or `label` (the adapter string mapper only reads `name`/`symbol`/`path`). Symbol context also binds `filePath` so exact-hit admission can reject without an LLM. Watcher `searchExisting`, `orch code search`, and plan draft/reuse also query the global admission ledger so reserved files/symbols/deps show up as existing hits even when the CLI or plan path constructs its own GitNexus adapter. The watcher persists deleted symbols and affected processes onto the task so the TUI admission panel, serve JSON logs, `orch logs --follow`, and TUI live feed can report them. The TUI task detail also shows `task.workspace` so operators can confirm GitNexus was bound to the worker worktree, not the repo cwd.
- Fast-path contracts allow edits in scope only. `allowed_new_files`, `allowed_new_symbols`, and `allowed_dependencies` start empty.
- Request creates with `orch admission request --task <id> --type new_file|new_symbol|new_dependency|scope_expansion`. Empty or "cleaner" why-not-reuse is rejected before the LLM for files, symbols, dependencies, and scope expansions. A new dependency must say why stdlib, an installed package, or an internal utility is not enough.
- The running ORCH watcher decides. You never approve your own request.
- Exact path / exact symbol / reserved name → auto-reject, reuse the existing surface, optionally `depends_on` the owner unless that edge would cycle.
- UNKNOWN or unresolved GitNexus impact is not LOW. Unspecified impact cannot auto-approve a high-risk existing-symbol edit. HIGH/CRITICAL is never automatic. `high_risk_edit` and security/auth/payments/concurrency/dataflow-sensitive requests fail closed unless `gitnexus analyze --pdg` runs (same gate as plan reuse).
- Unapproved files/symbols/dependencies fail the merge audit and the task stays in `review`.
- Shared-workspace audits also treat untracked files as added. They need admission like any other new file; `git diff` against the contract SHA cannot see them. If the working tree is dirty beyond `task.proof.files_changed`, the audit fails closed.
- Light CLI (`orch proof`, `orch admission audit`) audits `task.proof.branch` via git name-status against the merge-base, then staged/unstaged/untracked porcelain from that branch's worktree. An empty committed range is not a pass if a create is still uncommitted. Checking out main after the worker branch is not a pass. Unstaged or staged edits of existing files keep their `git diff HEAD` added lines so conventions/JSDoc and new `package.json` dependencies stay visible.
- Planned tasks keep `plan_id` / `plan_unit_id`. The Modification Contract also records `plan_digest` from `.orch/plans/<plan>.json` (computed from title+units when the file omitted one) so later audit and council can identify the exact plan version.
- When `.orch/workflow.yml` sets `conventions.enabled: true`, the same audit also applies spec §3.4 path/comment rules (`no_parallel_utils`, header-only comments, no function JSDoc, max new files). Failures stay `unapproved_file` and block merge-back. Those rules also belong in the worker prompt; merge-back and `orch proof` already enforce them even if a dispatch prompt injection is missing.
- Incomplete GitNexus reuse (`reuse.incomplete`) does not authorize `proposed_creates`. HIGH/CRITICAL/UNKNOWN `recommended_edits` are not stamped onto the Modification Contract — that list would otherwise authorize the edit. Candidates are still recorded so workers can investigate. Security/auth/payments/concurrency/dataflow-sensitive reuse queries request `gitnexus analyze --pdg` (not on every trivial plan). If that analyze cannot run, reuse is incomplete and creates stay unauthorized.
