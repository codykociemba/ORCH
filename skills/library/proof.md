# Proof

- Bind proof to the task branch SHA (`task.proof.branch`), not the checkout HEAD. Linear and GitHub both refuse to publish a proof comment without that SHA. MEDIUM GitNexus impact edits also require a passed test/typecheck check (`require_tests_for_dependents`); otherwise Verified is dropped and worktree merge-back is refused. `orch proof` uses `canonical-publish` wiki evidence only when the default branch can publish, bootstrap is done, and the GitNexus index is current. A later commit on the task branch clears stored Verified on the next watcher tick, and refuses merge-back / Linear / GitHub proof publish until proof is rebuilt for that SHA.
- Include code-admission PASS/FAIL, reused/modified symbol counts, blast-radius risk, approved vs actual new files/symbols/dependencies, and violations. Actual new dependencies come from the admission audit plus `package.json` added lines on the task branch. Outbox retry and `orch pr link` publishProof stubs also get this GitNexus admission block from the contract/ledger (they used to comment SHA-only). A live stale index drops Verified on that path. Deleted symbols, affected processes, admission request IDs, GitNexus repo, and the worker worktree path are stamped onto Linear/GitHub proof comments (branch is not the worktree). The TUI admission panel and serve JSON logs also report deleted symbols and processes.
- `orch proof <task-id>` renders the GitHub section.
- `orch proof publish <task-id>` comments Linear when configured and sets the `verified` label only for the current HEAD SHA. A later commit returns the issue to In Review.
- A failed or incomplete admission audit prevents Verified.
- A stale GitNexus index (`code_index.index_current: false` or wiki evidence `index_current: false`) prevents Verified. Wiki evidence itself reports `status: failed` and omits `pages_published` when the index is stale. Canonical wiki publish also refuses in that state. Wiki evidence `status: failed` (generate/module failure) also prevents Verified; `bootstrap_required` does not.
- Conventions lint (`.orch/workflow.yml` `conventions`, spec §3.4) is a proof check **and** part of the admission audit that already runs before merge-back. `orch proof` and `orch pr` lint `merge-base…task.proof.branch` (and `git show` added files from that ref). Empty `files_changed` still lints git-attributed files on the branch. Failed conventions cannot be Verified and cannot merge. Missing `conventions.enabled` skips the check.
- Review policy is `human_or_cursor` by default. Tasks labeled `high`, `critical`, `high-risk`, or `council-required`, or whose Modification Contract records HIGH/CRITICAL/UNKNOWN GitNexus impact, use `review.high_risk_policy` (`human_and_cursor` in this repo). UNKNOWN is not LOW. Cursor review ingest and the GitHub Action refuse to approve a review with no HEAD SHA. The Action also posts an `ORCH Cursor review` check bound to that SHA (`checks: write`; fork PRs still never see `CURSOR_API_KEY`). `orch task approve` / TUI approve bind the human review to the task branch SHA when checkout HEAD is a different ref. `orch proof` / PR proof / wiki announce also refuse Verified when HEAD still has `changes_requested` or `failed`, even if another reviewer approved that SHA. Worktree merge-back uses the same fail-close so a human approve cannot merge over an unresolved HEAD review. Linear and GitHub proof publishers also drop Verified in that case, so `orch pr link` cannot stamp the label around the CLI gate.
- Snapshots land in `.orchestry/proofs/<taskId>/<headSha>.json`.
- `orch pr create|link` stamps `task.proof.head_sha` from the task branch before Linear/GitHub proof, then writes that snapshot and updates the GitHub proof comment when a PR number exists. The PR body proof marker uses that SHA (`<!-- orch-proof:<taskId>:<sha> -->`) instead of a `HEADSHA` placeholder when proof is present. The ORCH section also names the assigned agent when `task.assignee` is set. Same-plan Linear siblings appear in the PR body (`Fixes` vs `Contributes to`); same-branch siblings also receive the PR link.
- Wiki evidence is included: preview on PRs, `canonical-publish` on the default branch after bootstrap, `bootstrap_required` until the first GitHub wiki page exists.
- After `orch wiki publish`, matching Linear issues and GitHub PRs get one wiki URL comment (not one per page). That comment is the same admission-bound proof as `orch proof` (audit + conventions + actual new dependencies), not a SHA-only stub.
- GitHub proof comment create/update retries twice on a transient `gh` failure before failing the publish.
